# ESP32 bring-up probe on hardware (2026-11-05)

The first code built by EmbCC for Xtensa to run on silicon, and the first run of the [Xtensa bring-up probe](../ports/xtensa.md). It is not a kernel run: the probe has no kernel, it shows that the toolchain, the image, the flasher and the register addresses are right.

**Board:** an "ESP-32S" development board (ESP-WROOM-32, classic ESP32, dual-core Xtensa LX6), CP2102 USB-serial bridge, `/dev/cu.usbserial-0001` on macOS. The ROM banner is `ets Jul 29 2019 12:21:46`, the ROM of chip revision 3.

**Image:** `tools/esp/bringup/build.sh` at this commit, with EmbCC 0.0.1-beta's `embcc` for `xtensa-none-elf` and the installed `embld`. That `embld` predates D-024, so `build.sh` linked with its fallback, `-Ttext 0x40080400 -Tdata 0x3FFF0000`. `esp32_hello.bin` has SHA-256 `1c69e143bce027901146115dd83ce6c54918264734b971622d4d1203079e9abe`, and `check_probe.py` accepts it.

**Flasher:** EmbCC's `embflash --esp` from branch `embflash-esp` at `dddd442c` (EmbCC #173), built from source: `embflash esp32_hello.bin --esp serial:/dev/cu.usbserial-0001 --base 0x1000 --verify`. It wrote one 1,024-byte block at 460,800 baud and checked the flash's MD5. The installed `embflash`, an older build of #173, sent FLASH_END at the end: the ROM wrote the image and then answered error 0x06, and embflash exited 2. The branch no longer sends FLASH_END, as esptool does not.

## The console

`docs/engineering/hil-runs/2026-11-05-esp32-probe/console.log`, after a reset into normal boot (EN through RTS, IO0 high):

```text
rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
mode:DIO, clock div:2
load:0x3fff0000,len:60
load:0x40080400,len:332
entry 0x40080468
emb: hello from the ESP32 (Xtensa LX6), line 0
emb: hello from the ESP32 (Xtensa LX6), line 1
```

The ROM loaded the DRAM segment (60 bytes at 0x3FFF0000) and the IRAM segment (332 bytes at 0x40080400) as `esp_image.py --chip esp32` laid them out, and called the entry. The probe stopped the three watchdogs, since the board printed without resetting, and printed through UART0 at the addresses from ESP-IDF v5.4.

## What it settles, and what it does not

Settled on the part: the windowed-ABI code EmbCC emits runs from IRAM and calls into the ROM's UART routines, the image format and the 0x1000 offset are right, the watchdog and UART register addresses are right, and embflash's ROM protocol works on this ROM. Not settled: anything of a kernel port. The window spill and fill around a context switch, the interrupt matrix, the CCOMPARE tick, the second core and the flash cache are the steps of the port page's "Before a core port" section.
