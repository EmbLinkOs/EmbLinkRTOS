# Where the notification hand-over's cycles go, and link-time optimization (2026-11-07)

On the NUCLEO-F446RE, built by GCC at `-Os` as FreeRTOS is, the notification hand-over took 794 cycles against FreeRTOS's 623 ([report](hil-nucleo-2026-11-07.md)). Under QEMU the two kernels' instruction counts for it differed by about 10% (A97), so the difference was in how the core runs the code.

This page records:
- the profile that found it;
- the build experiments that followed;
- the link-time optimization option that came out of them, [ADR-056](../architecture/06-decision-records.md).

Every figure is in CPU cycles at 180 MHz (DWT CYCCNT), from a release build, on the same board.

## The profile

`tools/hil/pcsample.py` read the Cortex-M4's PC sample register 50,000 times through the ST-LINK while each kernel ran the hand-over forever (`bench_compare.c` with `BENCH_PROFILE_NOTIFY`). The records and the images are in `hil-runs/2026-11-07-nucleo_f446re-notify-profile/`, with a `README.txt`. Cycles per round trip, two hand-overs:

| Group | EmbLinkRTOS | FreeRTOS V11.1.0 |
|---|---|---|
| Context switch: PendSV and exception entry | 262 | 155, and 149 in `vTaskSwitchContext`, which also picks the next task |
| Scheduler bookkeeping: `embk_sched_select`, `peek`, `insert`, `enqueue`, `make_ready`, `remove_ready`, `reschedule_slow`, `should_preempt`, `switch_away` | 514 | about 120 in list operations |
| Wait layer: `wait_common`, `embk_wait_prepare`, `commit`, `wake`, `block_on`, `timeout_disarm` | 425 | 78 (`prvAddCurrentTaskToDelayedList`) |
| Notification API | 307 | 364 |
| Critical sections, outside the functions above | inside the functions | 214 (`vPortEnterCritical`, `vPortExitCritical`) |
| The benchmark's own loop | 75 | 43 |
| Total | 1,587 | 1,246 |

The context switch is not the gap. The kernel's layers are:
- **EmbLinkRTOS:** about twenty small functions across `notify.c`, `wait.c`, `sched.c` and `time.c`, each call paying a branch, the pipeline refill and its register saves. GCC cannot inline across files without link-time optimization.
- **FreeRTOS:** its task logic is one file, `tasks.c`, where its static helpers inline.

## The build experiments

The same source, built several ways:

| Build of `bench_compare` | Notify switch | Sem switch | Give + take | ISR wake | Image text |
|---|---|---|---|---|---|
| EmbLinkRTOS `-Os` (the build until now; [NUCLEO report](hil-nucleo-2026-11-07.md)) | 794 | 746 | 194 | 1,514 | 11,080 B |
| EmbLinkRTOS `-Os`, rebuilt in the experiments' session | 800 | 765 | 194 | 1,533 | 11,080 B |
| EmbLinkRTOS `-O2` | 706 | 700 | 173 | 1,402 | 11,880 B |
| EmbLinkRTOS, kernel's hot files as one translation unit, `-Os` | 921 | 864 | 217 | 1,651 | 10,920 B |
| **EmbLinkRTOS `-Os` + LTO (`EMB_LTO`)** | **632** | **648** | **191** | **1,285** | **9,128 B** |
| EmbLinkRTOS `-O2` + LTO | 512 | 538 | 147 | 1,076 | 10,248 B |
| FreeRTOS V11.1.0 `-Os` | 623 | 831 | 178 | 1,474 | 7,056 B |
| FreeRTOS V11.1.0 `-Os` + LTO (`BENCH_LTO=1`) | 565 | 731 | 131 | 1,328 | 6,192 B |

- **Comparing within a session:** the `-O2` and unity rows were measured in the same session as the rebuilt `-Os` row. Its source carried the profiling switch, which moves code slightly. Compare those rows with that baseline.
- **Results:** LTO takes 17–20% off every switching path and 18% off the image. Nothing else does both.
- **The unity build:** compiling the kernel's hot files as one translation unit (CMake's `UNITY_BUILD`) made the image slightly smaller but every path slower. It inlines only within the kernel, not into the application or the port, and the Cortex-M4's flash accelerator is sensitive to the different layout. It was not pursued.
- **The `-Os` + LTO row** is from the final build, with `-fno-ipa-reference` (below). Without that flag the first measurement was 639, 631, 191 and 1,278: within noise, with no cost.
- **FreeRTOS gains from LTO too.** Built the same way, at `-Os` with LTO, the comparison stands:
  - notification hand-over: 632 against 565 (+12%);
  - semaphore hand-over: 648 against 731 (−11%);
  - give and take: 191 against 131 (+46%);
  - interrupt wake: 1,285 against 1,328 (−3%).

  The give-and-take gap grew: FreeRTOS's semaphore calls inline into the caller's loop, ours keep the handle's validation. It is the next profile.
- **The interrupt latency.** `bench_irq`'s average from the pend to the handler fell from 153 to 107 cycles with LTO, and to 100 with Clang.

## What LTO needed (ADR-056)

`EMB_LTO=ON` turns on CMake's interprocedural optimization for every target: the kernel, the port, the board, the tests and the application.

| What LTO did | What it needed |
|---|---|
| Dropped what only assembly or a linker script references: the Cortex-M interrupt stack (the board faulted at reset, its MSP below RAM), PendSV's switch state, the fault handler, the AVR's current thread, `embk_isr_enter`/`exit`, `embk_thread_launch` | `EMB_USED` on each |
| Turned the layout probe's markers into bitcode | the probe opts out |
| Saw the slim idle context's deliberately different type (ADR-050) | under LTO, the full control block |
| Folded a static across a kernel call that ran another thread: `test_smoke`, `test_timer`, `test_irq` failed under GCC | `-fno-ipa-reference` (GCC) |

The folding is the one that matters beyond this kernel:
- **What happened:** GCC's ipa-reference pass saw the whole call graph, but not the switch, which happens in PendSV or an interrupt. It concluded that a static, written only by a thread entry and never address-taken, survived the call unchanged. The asm `"memory"` clobbers do not cover such a static.
- **Why it was new:** without LTO the kernel call is opaque and may reach any address-taken function, so the static is reloaded.
- **The fix:** `-fno-ipa-reference` restores that.
- **Clang:** its ThinLTO passed every suite without it.

## The uncontended give and take, and EMBK_HOT

After LTO the widest gap was the uncontended give and take on one thread: 191 cycles against FreeRTOS's 131, both built with LTO. A profile of each (`bench_compare.c` with `BENCH_PROFILE_GIVE_TAKE`), cycles per give and take:

| EmbLinkRTOS, LTO | Cycles | FreeRTOS V11.1.0, LTO | Cycles |
|---|---|---|---|
| `emb_sem_take` | 70 | `xQueueSemaphoreTake` | 38 |
| `emb_sem_give` | 50 | `xQueueGenericSend` | 32 |
| `embk_obj_from_raw`, the handle check, twice | 25 | `vPortEnterCritical`, `vPortExitCritical` | 50 |
| `embk_sched_reschedule_if_needed` | 16 | | |
| `embk_wait_first` | 9 | | |
| `embk_thread_take_cancel_locked` | 8 | | |
| the loop | 13 | the loop | 11 |

The four helpers in the middle are each a test or two:
- **Why they were calls:** they were declared `inline`, but GCC at `-Os` keeps a widely used inline function out of line, because one call is smaller than many copies. Every give and take paid a call and a return for each.
- **The fix:** `EMBK_HOT` makes them always inline where the word is 32 bits, and stays a hint on 8- and 16-bit ports, where the call is the smaller code.
- **The waiter check:** `embk_wait_first` moved from `wait.c` into its header.

Same session, cycles per operation:

| Build | Notify | Sem | Give + take | ISR wake | Image text |
|---|---|---|---|---|---|
| without LTO | 800 | 765 | 194 | 1,533 | 11,080 B |
| without LTO, `EMBK_HOT` | 784 | 738 | 180 | 1,503 | 11,032 B |
| LTO | 632 | 648 | 191 | 1,285 | 9,128 B |
| **LTO, `EMBK_HOT`** | **616** | **623** | **146** | **1,272** | 9,144 B |
| FreeRTOS V11.1.0, LTO | 565 | 731 | 131 | 1,328 | 6,192 B |

- **Against FreeRTOS:** the give-and-take gap falls from 46% to 11%. The notification hand-over is 9% behind, and the semaphore hand-over and the interrupt wake stay ahead.
- **What remains:** the profile now shows only `emb_sem_take`, `emb_sem_give` and the loop. The rest of the difference is the API's own contract: the handle check, the cancellation check and the scheduler lock.
- **AVR:** the T1 sample is 12 bytes smaller (avr-gcc 14.4.0).
