# Specification amendments recorded during M4

Changes M4 makes to accepted specifications and requirements, where an accepted document is narrowed, extended or made concrete. Each is applied in the affected document when M4 implements it; this page keeps the audit trail. Numbering continues from the [M3 record](AMENDMENTS-M3.md).

**Status:** proposed with M4.0 (2026-11-09), awaiting the project owner's review.

| # | Document | Amendment | Where in the code |
|---|---|---|---|
| A108 | SPEC-011 §9, PORT-008, SPEC-018 §7 | **Sleep in the port contract.** SPEC-011 §9 listed `emb_arch_sleep(emb_power_state_t)` as planned and absent, while PORT-008 already required it to enter the power core's mapped state. It becomes `void emb_arch_sleep(void)`: the core's deep sleep (on Cortex-M, SLEEPDEEP set and `wfi`), entered with interrupts masked so a wake-up is not lost, as `emb_arch_idle` does. What a state needs from the SoC before and after (the regulator, flash power, the clocks to restore) is the SoC's, in `emb_soc_power_enter(state)` and `emb_soc_power_exit(state)`, so the port knows no SoC. A port provides `emb_arch_sleep` only when its manifest declares `power.sleep: true`; `CONFIG_EMB_PM` on a port without it is refused at configuration. PORT-008's second clause reads: "with `CONFIG_EMB_PM`, `emb_arch_sleep` shall enter the core's deep sleep after the SoC prepared the state, without a window in which a wake-up can be lost." | `arch/cortex_m/cm_port.c`, `soc/*/power.c` (M4.4) |
| A109 | 04 §3.2, SPEC-017 §7, A83 | **DMA and caches.** The checklist's "DMA ownership and cache maintenance" is answered for M4's targets: the Cortex-M4F and the Cortex-M33 have no data cache, and the Cortex-M7 runs with its caches off (A83), so no driver performs cache maintenance. Where a DMA buffer may live is the description's `dma` region attribute (SPEC-014 §3), which the DMA class checks. A port whose core has a data cache enabled must provide clean and invalidate operations before any DMA class is claimed on it. | `drivers/*/…_dma.c` (M4.2) |
| A110 | SPEC-014 §3, SPEC-018 §2.2 | **Power states in the SoC description.** `power.states` entries gain `class` (IDLE, SLEEP, DEEP_SLEEP or OFF), `entry_us`, `exit_us` (replacing `exit_latency_us`), `min_residency_us`, `wake` (the wake sources), `timebase` (what keeps time while the main timer is stopped) and `retains`, beside `loses`. The figures start as the datasheet's and are replaced by measurements (PWR-006). The generator emits the table the policy reads. | `hw/schemas/soc.schema.json`, `hw/gen/emb_hwgen/` (M4.4) |
| A111 | SPEC-014 §4, §7, SPEC-019 §3 | **The `boot` key and the image's partitions.** A board may declare `boot: {loader: mcuboot, header_size, mode}`. With it, `flash_partitions` must name `bootloader`, `slot0`, `slot1`, and `scratch` for `mode: swap_scratch`; each partition is whole sectors of the flash's geometry, the slots are equal, and the scratch is at least the largest sector a slot uses. The application links at `slot0` plus `header_size`, and the refusal of an application partition away from the boot base applies only to boards without `boot`. | `hw/gen/emb_hwgen/model.py` (M4.5) |
| A112 | SPEC-014 §4, ADR-059 | **The board's system timer.** A board may name `system_timer: <peripheral>`, the SoC timer that keeps tickless time (ADR-059). The generator checks that the peripheral is a timer whose features the port's tickless hooks need (a free-running counter of at least 32 bits and a compare or alarm), and declares the architecture's tickless capability for that board only. | `hw/gen/emb_hwgen/`, `arch/cortex_m/` (M4.4) |

**Not an amendment:** writing the vector table base (VTOR) at reset is already `emb_arch_early_init()`'s duty in SPEC-011 §4. The Cortex-M port has not done it, because every image so far boots from the boot base; M4.5 implements it for images in a slot (SPEC-019 §3).
